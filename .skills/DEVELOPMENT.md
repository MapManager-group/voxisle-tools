# VoxIsle Tools 后续开发规范

本文是本仓库后续开发的执行约定。视觉规范以 `DESIGN.md` 为准，接口行为以对应的 `*-API.md` 为准；发生冲突时，先确认契约再修改实现，不凭经验猜测。

## 1. 开发前检查

开始编码前必须先完成以下检查：

1. 阅读项目目录、`../package.json`、入口文件及本规范。
2. 阅读完整的 `DESIGN.md` 和本次功能涉及的 API 文档。
3. 检查 `.skill`、`AGENTS.md` 或其他仓库级指导文件；存在时必须遵循。
4. 查找已有布局、组件、工具函数和同类页面，优先复用现有所有者。
5. 确认当前工作区已有改动，避免覆盖无关代码。

不得在没有实际检查代码和配置的情况下宣称已经熟悉项目。

## 2. 目录与职责

```text
src/
├── components/
│   ├── layout/       # 应用壳层、导航、页头、页脚等固定结构
│   └── ui/           # 无业务含义的通用视觉组件
├── features/
│   └── <feature>/    # 页面、功能内部组件和功能状态
├── lib/              # 无界面的通用工具与 API 辅助函数
├── config.ts         # 环境变量映射和全局公共类型
├── App.tsx           # 路由与顶层页面选择
└── main.tsx          # React 启动入口
```

- 通用组件不得依赖具体业务页面。
- 功能专属组件保留在对应 `features/<feature>` 内，不提前抽象。
- `App.tsx` 不承载表单、请求或大段页面结构。
- Header、Footer、Sidebar 等固定结构必须放在 `components/layout`。
- React 使用函数组件和 Hooks；除非已有明确需要，不引入旧式类组件。

## 3. 配置与环境变量

所有 API 基础地址、CDN 地址和随部署环境变化的外部地址都必须使用 Vite 环境变量，不得硬编码在组件或请求函数中。

当前变量：

| 变量                          | 用途                         |
|-------------------------------|------------------------------|
| `VITE_QR_API_BASE_URL`        | 二维码服务基础地址           |
| `VITE_SCHEMATIC_API_BASE_URL` | Schematic Cloud 服务基础地址 |
| `VITE_LOGO_CDN_URL`           | 品牌 Logo 地址               |

- 本地默认值写入 `.env`，可复制的配置模板维护在 `.env.example`。
- 客户端可读取的变量必须以 `VITE_` 开头。
- 不得把密码、Token、删除密钥或其他秘密写入 `VITE_` 变量；Vite 会将其暴露到浏览器产物。
- 组件只从 `../src/config.ts` 读取配置，不直接散落访问 `import.meta.env`。
- 拼接接口路径时以 API 文档为准，避免重复或遗漏斜杠。

## 4. 组件与状态

- 相同的按钮、字段、卡片、通知和空状态必须复用 `components/ui`。
- 页面只组合组件并管理本功能状态；跨页面确实需要共享时再提升状态。
- 使用原生语义元素：操作使用 `button`，导航使用 `a`，表单项具备标签和可访问名称。
- 异步操作必须包含忙碌、成功和失败状态，并阻止重复提交。
- 字段错误显示在相关区域附近，保留用户已输入或已选择的数据。
- 不使用浏览器 `alert`、`confirm` 或 `prompt` 代替产品界面反馈。
- 不为单一调用创建接口、工厂或状态框架；优先使用平台能力和现有依赖。

## 5. 视觉与响应式

- 严格遵循 `DESIGN.md` 的颜色、圆角、间距、字体、深色模式和语义色规则。
- 系统级样式由共享样式和共享组件维护，不在业务页面复制色值或建立局部设计系统。
- 桌面侧栏显示完整品牌与菜单；窄屏收起文字但保留图标、可访问名称和悬停提示。
- 页面保持自然文档滚动，不给共享壳层添加不必要的固定高度或隐藏溢出。
- 所有交互提供可见键盘焦点；动画遵循 `prefers-reduced-motion`。
- 修改共享组件后必须检查两个现有页面，避免只验证当前页面。

## 6. API 与文件安全

- 请求字段、方法、状态码和响应类型必须与 `qrcode-generate-API.md`、`schematic-cloud-API.md` 一致。
- 上传使用 `FormData` 时不得手动设置 `Content-Type`，由浏览器生成 multipart boundary。
- 二进制下载不得按 JSON 解析；错误响应优先依据 HTTP 状态码，再读取服务端错误文本。
- 下载密钥可以分享；删除密钥视为密码，不写入 URL 参数、日志、通知或持久化存储。
- 对象 URL 使用后必须调用 `URL.revokeObjectURL`，避免长期占用内存。
- 不新增未经需求授权的删除、权限或其他高风险操作。

## 7. 改动范围

- 优先修改真正拥有该行为的共享组件或工具函数，避免在多个页面重复修补。
- “仅修改展示”类需求不得改动 API、路由、状态模型或业务流程。
- 不顺手重构无关区域，不升级依赖，不改变公开契约，除非任务明确要求。
- 发现相邻问题时记录并说明，不把它混入当前改动。

## 8. 完成标准

每次提交前至少执行：

```bash
npm run lint
npm run build
```

同时人工检查：

- 两个页面均可正常切换；
- 宽屏和窄屏侧栏行为正确；
- 键盘焦点、加载、成功、失败和空状态可识别；
- 浅色与深色模式内容可读；
- 环境变量缺失或 API 不可达时错误信息明确；
- 没有把密钥、临时文件或构建产物意外提交。

报告验证结果时必须区分：静态检查、生产构建、浏览器交互和真实 API 联调。某一层未执行时应明确说明，不能用构建成功代替线上可用性结论。
